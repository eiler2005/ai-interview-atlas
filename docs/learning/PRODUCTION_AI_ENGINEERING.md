# Production AI engineering: eight-week practice route

[English](PRODUCTION_AI_ENGINEERING.md) · [Русский](../ru/learning/PRODUCTION_AI_ENGINEERING.md) · [Learning path](../LEARNING_PATH.md) · [Engineering](../start/engineering.md)

This route helps experienced developers explain the design and operation of a bounded service around a model. It sits inside AI Engineering alongside [AI-assisted coding](AI_ASSISTED_CODING.md). The existing eight-week learning path remains the broad foundation, including attention, training and specialisms. Here the emphasis is contracts, evaluation and operational judgement.

Plan **eight weeks at 6–8 hours per week**, an editorial estimate rather than a measured preparation time. Prerequisites are familiarity with small services, HTTP failures, asynchronous work, databases and held-out evaluation. Use the baseline learning path to close those gaps. The current route requires questions, reading, explanations and checklists. **Python labs, service implementation and an AI evaluator are deferred by the maintainer's current scope.** Completion does not certify production readiness or predict hiring.

## One conceptual case throughout

Consider an assistant for an invented equipment-maintenance catalogue. It would answer from versioned manuals and propose a maintenance ticket. Two fictional user groups have different document access. Reason about answerable, unsupported and forbidden requests; no dataset creation, model account, API key or running service is required. These editorial follow-ups are outside the published and radar-generated bank.

Keep the proposed boundaries explicit: no action merely because a model requests it, no answer from forbidden documents, an insufficient-evidence response, a release owner and a per-request time, usage and retry budget. Separate what a design promises from what only an implemented test could establish. Read the primary materials attached to the linked questions, then use the written answers as one defensible approach rather than a script.

## Eight modules

Reserve 1–1½ hours for reading, 3–4 hours for question analysis and a short decision note, 1 hour for oral explanation and 1–1½ hours for feedback and delayed retries. Evaluation and access control begin in the first module.

## Four distinctions to keep explicit

**Format and meaning.** Schema conformance does not establish factual accuracy or business validity. Provider behaviour is version-specific: [Claude's documentation](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) lists refusal, token-limit and enum-case exceptions. Validate completion and application rules; do not retry indefinitely.

**Repeatable checks and variable outcomes.** A fixed dataset does not make model outputs or graders deterministic. [Anthropic's evaluation account](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) discusses grader types and calibration. Explain repetitions, disagreement and failure severity; an average gain cannot cancel a permission leak.

**Filtering and authority.** Input sanitisation alone is not a security boundary. [OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) describes controls including least privilege and separation of external content. Authorisation belongs in application code and must cover retrieval, tools, caches and logs.

**Protocol and trust.** MCP standardises integration; it does not establish trust in a server or its tools. The [dated security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) covers token audience, consent, SSRF and local-server risks. Name who grants authority, its resource scope and revocation. A protocol-only diagram is insufficient.

## Completion and limits

Use the [existing 0–3 rubric](../LEARNING_PATH.md#3-use-a-practice-loop-with-evidence). Each module's explanation and delayed attempt need **at least 2**: an independently explained mechanism, assumptions, trade-off and relevant check. A 3 also handles a changed constraint and failure case. Scores 0–1 require review; a critical correctness or access error blocks the gate regardless of average score. Retry after roughly two days and the following week, recording date, feedback and the next weak point.

You can complete the current route without running a model. That demonstrates reasoning, not measured answer quality, latency, refusal behaviour or injection resistance. A future implementation could use synthetic data and deterministic stubs without API keys, but even passing stub tests would establish control flow only, not live-model quality. Do not claim unperformed checks.
