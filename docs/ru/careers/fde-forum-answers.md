## <a id="interest-app"></a>1. Декомпозиция приложения для обмена интересами

**Из рассказа:** материал о Palantir, опубликованный в марте 2025 года, включает обмен интересами и последующий вопрос о дополнительных функциях. Социальная сеть, модель рекомендаций и масштаб не заданы.

**Развёрнутый ответ.** Начните с вопроса: «Кто чем делится, с кем и какое полезное взаимодействие должно произойти дальше?» Для учебной версии примем добровольное сообщество: участники указывают интересы и находят людей с общим интересом. Первый сквозной процесс: изменить интересы → найти подходящих людей → посмотреть профиль → запросить контакт. Модель включает `User`, `Interest`, `UserInterest`, `ContactRequest` и `Block`. Храните идентификатор интереса отдельно от отображаемого названия: переименование не должно ломать совпадения. Проверки членства, видимости и блокировок выполняются на сервере.

`PUT /me/interests` проверяет допустимость идентификаторов и заменяет набор. `GET /people?interest_id=...` возвращает только разрешённые видимые профили с пагинацией. `POST /contact-requests` проверяет доступ повторно: после поиска профиль мог стать закрытым. Ограничение уникальности активного запроса предотвращает дубли. Начните с детерминированного подбора и реляционного хранилища; ранжирование добавляйте после выяснения, что означает полезное знакомство. Измеряйте принятые полезные контакты и жалобы на нежелательные обращения, а не только клики.

**Уточнение.** «Что ещё реализовать?» Выводите функции из незавершённых процессов: отмену и отклонение запроса, блокировку и жалобу, удаление данных и управление видимостью. История встреч и рекомендации нужны только тогда, когда этого требует согласованный сценарий. Не добавляйте чат, ленту и ML ради заполнения схемы.

**Типичная ошибка:** обсуждать шардинг до определения одного взаимодействия. **Самопроверка:** проведите запрос от клиента через проверку прав, изменение состояния и ответ; объясните одновременные запросы и отзыв видимости.

## <a id="search-contract"></a>2. Реализовать явно выбранный контракт поиска

**Из рассказа:** `search(user_id, users)` с предоставленными классами. Классы, тип результата и ограничения не опубликованы. Функция ниже — **наш пример**, а не восстановленное условие.

**Учебные допущения:** `users` — словарь с целочисленными ID в ключах. Запись содержит множество канонических ID интересов, флаг `discoverable` и множество ID заблокированных людей. Вернуть других видимых участников хотя бы с одним общим интересом; исключить блокировку в любом направлении; отсортировать по числу общих интересов по убыванию, затем по ID по возрастанию. Неизвестный инициатор вызывает `KeyError`; отсутствие интересов даёт пустой результат. Аутентификация и полная политика доступа не входят в этот пример в памяти.

```python
def search(user_id, users):
    caller = users[user_id]
    result = []
    for other_id, other in users.items():
        if other_id == user_id or not other["discoverable"]:
            continue
        if other_id in caller["blocked"] or user_id in other["blocked"]:
            continue
        shared = len(caller["interests"] & other["interests"])
        if shared:
            result.append((other_id, shared))
    result.sort(key=lambda item: (-item[1], item[0]))
    return [other_id for other_id, _ in result]
```

При `U` пользователях, не более `I` интересов у каждого и `M` совпадениях ожидаемая сложность — `O(U·(1 + I) + M log M)` при обычном поведении хеш-множеств; дополнительная память — `O(M + I)` с учётом временного пересечения. Перебор занимает `O(U)` даже при пустых множествах интересов. Это удобная исходная реализация: её корректность легко проверить. Production-индекс должен сохранять все фильтры, а не просто быстрее выдавать похожий результат.

**Пример проверки:** у инициатора 1 интересы `{music, running}`; у 2 совпадает music, у 3 — оба интереса, у 4 тоже оба, но он блокирует 1. Ответ — `[3, 2]`. Добавьте равные оценки для проверки порядка по ID. Также проверьте неизвестного инициатора, отсутствие интересов, все закрытые профили, одностороннюю блокировку и отсутствие совпадений.

**Уточнение:** повторяющиеся запросы могут использовать индекс интерес→ID участников, затем подсчёт пересечений и фильтрацию доступа. Изменение интересов или прав требует обновления либо инвалидации индекса. **Типичная ошибка:** незаметно придумать исключение уже встречавшихся людей или формулу релевантности и выдать за исходное условие. **Самопроверка:** сможет ли другой человек написать тесты по вашему контракту, не уточняя слово «совпадение»?

## <a id="search-indexes"></a>3. Ускорить историю встреч и поиск в массиве

**История встреч.** Уточните запрос: «встречались ли эти люди?», «когда последний раз?» или «все встречи за период». Для существования встречи множество канонических пар `(min(a,b), max(a,b))` заменяет перебор ожидаемо константной проверкой вхождения; память линейна по числу разных пар. Для последней встречи храните пару→последняя дата. Для временного интервала нужен отсортированный список событий по паре с поиском границ; булево множество на такой запрос не ответит. Направленные взаимодействия требуют упорядоченных пар. До кеширования определите удаление, исправление и конкурентное обновление записей.

**Массив интересов.** Точное и префиксное совпадение — разные операции. В учебном примере массив содержит отсортированные уникальные строки с уже выполненной нормализацией и не меняется во время запроса. Найдите начало возможных совпадений, затем переберите их непрерывный участок:

```python
from bisect import bisect_left


def prefix_matches(sorted_interests, prefix):
    if not prefix:  # Учебная политика: не принимать неограниченный запрос.
        raise ValueError("prefix must be non-empty")
    i = bisect_left(sorted_interests, prefix)
    matches = []
    while i < len(sorted_interests):
        value = sorted_interests[i]
        if not value.startswith(prefix):
            break
        matches.append(value)
        i += 1
    return matches
```

Для `["art", "arts", "music"]` и `"art"` возвращаются первые два элемента; для `"z"` — ни одного. При ограниченной длине строк запрос занимает `O(log N + K)` для `K` результатов и `O(K)` памяти ответа; посимвольное сравнение добавляет зависимость от длины строк. Начальная сортировка требует `O(N log N)` сравнений, вставка в список Python — линейная. Нормализация должна одинаково применяться к данным и запросам; один `casefold()` не определяет правила диакритики и локали. [Документация Python bisect](https://docs.python.org/3/library/bisect.html) объясняет позицию вставки и линейную стоимость самой вставки.

**Уточнение:** при преобладании записей пересмотрите структуру или обновляйте пакетами; требование массива не делает повторную сортировку бесплатной. **Типичные ошибки:** бинарный поиск только по первой букве, предположение, что подстроки образуют непрерывный диапазон, и обещание логарифмической работы при выдаче тысяч результатов. **Самопроверка:** целое слово как префикс, отсутствующий префикс, префикс длиннее слова и выбранная политика пустого запроса.

## <a id="recipes"></a>7. Подобрать рецепты и обеспечить согласованность бронирования

**Учебный контракт:** ингредиенты имеют канонические ID, количество каждого измеряется в общей для него единице, значения неотрицательны; рецепт доступен, если хватает каждого требуемого количества. Замены, аллергии и частичный список покупок не подразумеваются: для них нужны отдельные требования. Прямая реализация:

```python
def feasible_recipes(stock, recipes):
    # recipes: {recipe_id: {ingredient_id: required_quantity}}
    return [
        recipe_id
        for recipe_id, needs in recipes.items()
        if all(stock.get(ingredient, 0) >= amount for ingredient, amount in needs.items())
    ]
```

Для `M` суммарных требований к ингредиентам работа занимает `O(M + R)`, где `R` — число рецептов, при константном поиске по словарю; ответ — до `O(R)` памяти. Входная валидация отклоняет отрицательные количества и несовместимые единицы. Для точных количеств подходят десятичные числа или целые минимальные единицы вместо двоичных float. По этому контракту пустой рецепт доступен; отдельно решите, должна ли валидация его запрещать.

**Пример:** есть два яйца и 100 г муки. Рецепт с одним яйцом и 100 г муки доступен, с тремя яйцами — нет. Проверяется возможность приготовить **каждый рецепт по отдельности**. Это не обещание, что запасов хватит на все найденные блюда одновременно.

Бронирование повара — отдельный автомат: свободный слот → кратковременное удержание → подтверждение либо истечение/отмена. Подтверждайте слот и резерв продуктов атомарно или задайте компенсацию, если они принадлежат разным системам. Стабильный ID запроса и ограничение уникальности предотвращают дубли от повторов. Показанная доступность — снимок, а не резервирование.

**Уточнение:** индекс ингредиент→рецепты сужает кандидатов, но проверка количеств остаётся. **Типичные ошибки:** проверка множеств, когда важны количества; превращение независимой доступности в обещание всего меню; проверка слота без его резервирования. **Самопроверка:** отсутствующий ингредиент, точное равенство, нулевое количество, пустой рецепт, разные единицы и два клиента, бронирующих один слот.

## <a id="war"></a>8. Описать War для нескольких игроков до написания кода

**Из рассказа:** несколько игроков и три закрытые карты при равенстве. Нехватка карт, порядок банка и завершение игры не определены. **Наши учебные правила:** у каждого игрока очередь карт; ранги сравниваются численно; каждый активный игрок кладёт одну открытую карту. Максимальный ранг забирает банк, если нет равенства. При равенстве продолжают только лидеры: три карты закрыто, следующая открыто. Участник ничьей с менее чем четырьмя оставшимися картами отдаёт всё в банк и не продолжает. Если продолжить некому, симулятор возвращает терминальное состояние «бой не разрешён». Если может один, он делает необходимый взнос и выигрывает. Банк добавляется в порядке внесения. Первые взносы идут по ID; при каждой ничьей сначала отдают карты неспособные продолжить игроки по ID, затем способные продолжить — тоже по ID.

Внешний игровой цикл обрабатывает ноль или одного активного игрока; `battle` вызывается, только если карты есть минимум у двоих.

```text
battle(decks):
    contenders = игроки с непустыми колодами по ID
    pot = []
    каждый contender кладёт одну открытую карту в pot
    contenders = игроки с максимальным открытым рангом
    пока contenders больше одного:
        eligible = contenders с минимум четырьмя оставшимися картами
        по ID каждый не прошедший условие отдаёт все карты
        если eligible пуст: вернуть UNRESOLVED, pot
        по ID каждый eligible кладёт три закрыто и одну открыто
        contenders = eligible с максимальным новым открытым рангом
    добавить pot в очередь победителя; вернуть победителя
```

Нужна очередь с эффективным извлечением из начала, например Python [`deque`](https://docs.python.org/3/library/collections.html#collections.deque). Работа одного боя линейна по числу перемещённых карт; обоснованной фиксированной границы числа боёв во всей игре нет. Добавьте предел симуляции или обнаружение повторного состояния, возвращая «достигнут лимит» или «цикл», а не объявляя победителя. Ключ состояния включает порядок игроков и всех карт каждой колоды; обнаружение повторов расходует растущую память.

**Уточнение:** альтернативное правило нехватки карт меняется как явная политика, а не набор разрозненных веток. **Типичные ошибки:** допустить проигравшего игрока в продолжение ничьей, потерять ранний банк или предположить, что любая детерминированная игра завершится. **Самопроверка:** обычный бой, ничья двух из трёх, повторная ничья, один/ни одного способного продолжить и сохранность всех карт в колодах плюс банке. Различайте идентичность карты и ранг, чтобы равные ранги не схлопнулись.

## <a id="ownership"></a>9. Разделить достижимость владельцев и финансовые величины

**Из рассказа:** исправление BFS для владельцев компаний и количества долей, затем циклы. Модель данных отсутствует. Сначала спросите, что означает ребро: «владеет», «принадлежит», число акций, экономический процент или голосующий контроль. Это разные запросы.

Для учебной достижимости `owners[company]` перечисляет прямых владельцев. Вернём всех достижимых владельцев, исключая исходную компанию:

```python
from collections import deque


def reachable_owners(company, owners):
    seen = {company}
    queue = deque([company])
    while queue:
        current = queue.popleft()
        for owner in owners.get(current, []):
            if owner not in seen:
                seen.add(owner)  # Отмечаем при добавлении в очередь.
                queue.append(owner)
    return seen - {company}
```

Каждая достижимая вершина и ребро обрабатываются один раз: `O(V + E)` времени, `O(V)` памяти. Циклы обработаны для **достижимости**, но множество посещённых узлов не рассчитывает экономическое владение. В ромбе второй допустимый путь может давать дополнительный вклад; его исключение занижает результат.

Для явно заданной ациклической модели пропорционального участия перемножайте доли вдоль пути и агрегируйте разные пути динамическим программированием в топологическом порядке. Пример: A прямо владеет 10% C и 60% B; B владеет 50% C. Модельное прямое и косвенное участие A в C равно `0.10 + 0.60 × 0.50 = 0.40`. Это учебная экономическая модель, а не юридический вывод о бенефициаре или голосующем контроле. Количество акций разных эмитентов нельзя просто складывать; процентам нужны правильный знаменатель, класс и дата.

При перекрёстном владении произвольный обход путей повторно учитывает круговые доли. В определённой линейной модели возможны уравнения вида `x = d + W x`; смысл и ориентация `W` должны быть заданы, а сходимость суммы путей требует спектрального радиуса меньше единицы. Замкнутый цикл из 100%-ных долей может сделать систему вырожденной. Нельзя незаметно «исправить» это исключением посещённых узлов или ограничением ответа сверху. Уточните определение учёта и отклоните либо передайте на разбор неподдерживаемые структуры.

**Типичные ошибки:** путать достижимость с величиной, складывать проценты разных компаний и считать любой цикл безвредным. **Самопроверка:** цепочка, ромб, цикл, дублированное ребро, разные классы акций и отсутствующий знаменатель. Назовите, на что отвечает реализация, а на что намеренно не отвечает.

## <a id="elevator"></a>10. Спроектировать лифт с явными инвариантами

**Из рассказа:** проектирование лифта без размера здания, границ аппаратной части и требований к расписанию. Для практики примем одну кабину, пронумерованные этажи и симуляцию диспетчеризации; сертифицированное управление физической безопасностью вне упражнения.

Состояние кабины: этаж, направление, состояние дверей и режим обслуживания. Запросы — выбранные в кабине этажи и внешние вызовы с направлением. Используйте переходы, а не произвольное изменение этажа из любого кода. Команда движения требует подтверждённо закрытых дверей и допустимой цели; открытие — остановки на нужном этаже. Аварийный режим запрещает диспетчеризацию до назначенной процедуры восстановления. Реальные блокировки принадлежат системе безопасности, а не только булевому полю приложения.

Простой алгоритм собирает остановки по текущему направлению, затем разворачивается, когда впереди запросов нет. Повторные нажатия не создают дубли. На третьем этаже при движении вверх и запросах на пятый и второй обслуживаем пятый, затем второй; совместимый вызов с четвёртого, поступивший до его проезда, можно вставить. Явно определите момент обслуживания внешнего вызова противоположного направления. Если новые запросы впереди приходят постоянно, учитывайте возраст ожидания и задайте политику справедливости вместо обещания невозможности голодания.

Для нескольких кабин отделите диспетчер от контроллера каждой. Оценивайте время подачи с учётом положения, направления, очереди и вместимости: ближайшая кабина не обязательно быстрее выполнит уже обещанный маршрут. Перебор `C` кабин и их очередей — допустимая исходная реализация; измерьте спрос до сложного оптимизатора. Разделите назначение запроса и подтверждение выполнения, чтобы обрабатывать отказ кабины.

**Уточнение:** объясните переживание перезапуска и повторных событий кнопки. **Типичные ошибки:** начинать с иерархии классов, двигаться с открытой дверью и оптимизировать среднее ожидание, игнорируя худшее. **Самопроверка:** простой, повторные вызовы, запрос позади направления, полная кабина, авария, перезапуск и постоянный поток. Проведите одну последовательность событий через все переходы.

## <a id="temperatures"></a>11. Решить классическую Daily Temperatures

В рассказе C3.ai упомянута **небольшая вариация**, но отличие не раскрыто. Решаем классический учебный контракт: для каждой температуры вернуть число дней до **строго более тёплого** значения; ноль, если его нет. Это не реконструкция варианта из интервью.

```python
def days_until_warmer(temperatures):
    waits = [0] * len(temperatures)
    pending = []
    for day, value in enumerate(temperatures):
        while pending and temperatures[pending[-1]] < value:
            earlier = pending.pop()
            waits[earlier] = day - earlier
        pending.append(day)
    return waits
```

Стек содержит нерешённые индексы в возрастающем порядке времени с невозрастающими температурами. Новое большее значение разрешает последние меньшие; это их первый тёплый день, потому что более раннее подходящее значение уже удалило бы их. Равные значения остаются. Каждый индекс добавляется один раз и снимается не более одного раза, поэтому суммарное время — `O(N)`, хотя одна итерация может снять много элементов. Ответ и худший размер стека — `O(N)` памяти.

Для `[73, 74, 75, 71, 69, 72, 76, 73]` результат — `[1, 1, 4, 2, 1, 1, 0, 0]`. `[70, 70]` даёт `[0, 0]`. Проверьте пустой ввод, один день, возрастающую и убывающую последовательности. Сравните с простым квадратичным решением на малых входах для проверки инварианта.

**Уточнение:** «теплее или равно» меняет сравнение; нерегулярные даты требуют разности времени, а не индексов. Минимальная величина потепления — другое условие: не предполагайте, что тот же инвариант стека сохранится без изменений. **Типичная ошибка:** объявлять квадратичность по вложенным циклам без амортизированного анализа или снимать равные значения. **Самопроверка:** объясните, почему найден первый подходящий будущий день, а не просто любой более тёплый.

## <a id="learning"></a>12. Работать с незнакомой документацией и связанными данными

**Из рассказа:** Government FDSE — связанные наборы данных, схема и документация, реализация функций на интервью. Самого API и задач нет. Ниже — наш метод подготовки и пример.

Сначала прочитайте контракт, один пример и поведение ошибок. Определите типы входа/выхода, nullable-поля, пагинацию, порядок, изменяемость и внешние эффекты. Выполните минимальный допустимый вызов, посмотрите результат, затем реализуйте одно полное поведение. Выпишите неизвестности и спросите о той, которая блокирует корректность, до изучения всех методов API.

**Синтетическое упражнение:** `list_orders(customer_id, cursor)` возвращает `items` и `next_cursor`; `None` завершает обход. У заказа есть `id`, `status`, целое `total_cents` и `currency`. Нужно сложить завершённые USD-заказы клиента. Согласуйте, дают ли страницы стабильный снимок и повторяются ли ID. Если повторы возможны, дедуплицируйте по ID с явным правилом конфликтующих версий; не считайте заказ дважды. Другие валюты отклоняйте или группируйте отдельно, не складывая разные единицы. Для `N` строк перебор занимает `O(N)` времени, дедупликация — `O(N)` памяти. Если API гарантирует уникальный неизменяемый снимок, эту память можно не расходовать.

При проектировании по нескольким наборам сначала определите ключи и смысл одной строки, затем рисуйте сервисы. Соединение клиентов с заказами меняет кратность; соединение строк заказов с платежами может размножить суммы. Проверяйте уникальность и количество строк до и после соединений. Определите отсутствующие связи, границы прав и свежесть для пользовательского действия. Покажите конкретный пример от исходных строк до нужного экрана или результата.

**Уточнения:** Что если курсор повторился? Если страница упала после успешного чтения предыдущих? Создаст ли повтор дублированную запись? Читающую агрегацию можно перезапустить со снимка или продолжить с согласованным состоянием; внешней записи нужна отдельная стратегия идемпотентности. **Типичные ошибки:** верить названию метода вместо контракта и продолжать после необъяснимого роста числа строк. **Самопроверка:** пустая страница с дальнейшим курсором, null, дубли, разные валюты, отсутствующий ключ соединения и сбой после частичной обработки. Сначала назовите допущения, затем выбирайте обработку.
